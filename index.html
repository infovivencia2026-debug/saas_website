How it works

Six workflows. One spine.

Every screen in EduCloud is generated from a single module registry — the same table engine, drawer and form language, whether you're admitting a student or closing a vendor invoice.

Everywhere the campus is

Runs where your staff already work

Sidebar becomes a drawer, tiles fall to one column, tables render as stacked cards. Every tap target is at least 44px.

The registry

Adding a module is a config entry.

Roughly 48 modules are declared in one file. A tab is either a table described in a compact column DSL, or a bespoke view. No new page component unless the tab needs genuinely custom interaction.

Questions

The things people ask first

Is this a working product or a prototype?

Today it is a front-end prototype. The interface is real and fully clickable — routing, tabs, drawers, modals, tables, search, filter, sort, pagination, row selection, bulk actions, form validation and drag-and-drop boards all work. The data behind it is generated in the browser, and there is no backend, database or authentication layer yet.

What happens if I refresh the page?

Records reset to their seeded values, because state lives in memory. Theme, sidebar state and the selected role persist in local storage.

Which parts are simulated?

All data. Also: "saved to server" messaging, exports, prints and downloads (they raise a toast), integrations, device feeds, AI predictions, payments, notifications, emails, and login.

How does role switching work?

Thirteen roles ship in the registry. Switching role from the avatar menu changes which modules appear in the sidebar and command palette, and drops you on that role's home module. Student, parent and faculty roles land in their own portals.

How hard is it to add a module?

Usually one registry entry. A tab is declared as a list of typed columns — type:Label@Option,Option — and the generator produces plausible records seeded on module:tab, so the same tab shows the same data across reloads. Bespoke tabs key into a custom views map instead.

Does it work on a phone?

Yes. Desktop keeps a fixed sidebar and wide tables; tablet collapses the sidebar and scrolls tables horizontally; phones get a drawer sidebar, single-column tiles and tables rendered as stacked cards.

What would a real deployment need?

An API and database behind the module registry, an authentication and permission layer to enforce what role switching currently only presents, and real integrations for payments, messaging and device feeds. The interface layer is the part that exists today.
