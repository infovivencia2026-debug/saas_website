The platform

What every suite gets for free

Building the fifth vertical costs what the second did, because the behaviour that makes a product usable is written once and inherited.

One table engine

Search, multi-column sort, filter, pagination, row selection and bulk actions — identical in a BOQ, a ward census and a fee register.

Roles that scope the app

Switching role changes the sidebar, the command palette and the landing screen. A site engineer and a finance controller never meet each other's modules.

A registry, not a rebuild

A module is a config entry: typed columns in a compact DSL, or a bespoke view when the tab genuinely needs one.

Desk, tablet or phone

Fixed sidebar and wide tables on desktop; a drawer, single-column tiles and stacked cards on a phone, with 44px tap targets throughout.

Shared back office

Sixteen modules every suite inherits.

Finance, people and procurement do not change because the industry does. They are written once and mounted into all five products, so a hospital and a plant close their books through the same ledger.

Questions

The things people ask first

Are these five separate products or one?

Both, deliberately. Each suite is bought and used as its own product, with its own modules, roles and vocabulary. Underneath they are one codebase and one registry, which is why the fifth vertical costs what the second did.

What is actually shared between them?

Sixteen back-office modules — general ledger, payables, receivables, costing, tax, workforce, attendance, payroll, talent, sourcing, purchasing, orders, analytics, administration, integrations and settings — plus the entire interface layer: tables, drawers, modals, forms, command palette and theming.

Is this a working product or a prototype?

Today it is a front-end prototype. The interface is real and fully clickable — routing, tabs, drawers, modals, search, filter, multi-column sort, pagination, row selection, bulk actions, form validation and drag-and-drop boards all work. The data behind it is generated in the browser, and there is no backend, database or authentication layer yet.

How hard is it to add a module, or a sixth industry?

A module is usually one registry entry: a list of typed columns written as type:Label@Option,Option. A new industry is a file declaring its modules, groups and roles, which then inherits the shared back office and every interface behaviour automatically.

How does role switching work?

Each suite ships its own roles — thirteen in education, eight in healthcare, seven each in construction, logistics and manufacturing. Switching role changes which modules appear in the sidebar and command palette, and lands you on that role's home screen.

Does it work on a phone?

Yes. Desktop keeps a fixed sidebar and wide tables; tablet collapses the sidebar and scrolls tables horizontally; phones get a drawer sidebar, single-column tiles and tables rendered as stacked cards.

What would a real deployment need?

An API and database behind the registry, an authentication and permission layer to enforce what role switching currently only presents, and real integrations for payments, messaging and device feeds. The interface layer is the part that exists today.
